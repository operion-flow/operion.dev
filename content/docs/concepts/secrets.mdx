---
title: Secrets
description: Credentials come from the server's environment as OPERION_SECRET_ variables, and executions never store their values
---

Operion does not store credentials. Whoever runs it puts them in the server's environment, named `OPERION_SECRET_<NAME>`, with the tools they already use: a Kubernetes `Secret`, Vault Agent, a compose file. `serve` and `operion run` read them once at start.

```bash
OPERION_SECRET_CRM_TOKEN=... OPERION_SECRET_SLACK_WEBHOOK_URL=... operion serve
```

A node reads one with `secret` and the name in lowercase, without the prefix:

```json
{
  "url": "https://crm.example.com/employees",
  "headers": {"Authorization": "Bearer {{secret \"crm_token\"}}"}
}
```

A name that is not set fails the node with `secret not found: <name>`. Templates read no other environment variable, so `DATABASE_URL`, `OPERION_API_TOKEN` and the rest of the server's settings stay out of reach.

## Masking

Before Operion stores anything a node produced, every secret value of 8 characters or more becomes `***`: node results, error messages, the data of a waiting node, retry errors and the execution's `error_message`. The node that called the CRM above sends the real token, and the execution shows `Bearer ***`.

Values shorter than 8 characters are not masked, the same rule GitLab and Windmill apply, so that short strings do not hide unrelated text. A node that receives a masked result sees `***`, so read the secret again with `secret` where it is needed.

## Scope

Secrets belong to the installation: the workflows of every [tenant](/docs/concepts/tenants) can read every `OPERION_SECRET_` variable. Run one Operion per company when companies must not share credentials.

Changing a secret takes a restart, since it is read at start.

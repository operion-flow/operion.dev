---
title: Secrets
description: Keep credentials out of workflows, encrypted per tenant and masked in executions
---

A credential such as an API token or a Slack webhook URL does not belong in the workflow JSON. Each tenant keeps its credentials as secrets, and nodes read them by name.

## Save a secret

```bash
curl -X PUT localhost:9091/secrets/crm_token \
  -H 'Authorization: Bearer dev-token' -H 'X-Tenant-Id: acme' -H 'Content-Type: application/json' \
  -d '{"value": "the-crm-api-token"}'
```

The answer is `204`. Saving a name again replaces its value. A name is a lowercase letter followed by up to 63 lowercase letters, digits or underscores.

`GET /secrets` lists the tenant's secrets with `name` and `updated_at`, and `DELETE /secrets/:name` removes one. No route returns a value; see the [API reference](/docs/reference/api#secrets).

## Use it in a node

A [template](/docs/concepts/templates) reads a secret with `secret`:

```json
{
  "id": "crm",
  "type": "httprequest",
  "category": "action",
  "config": {
    "url": "https://crm.example.com/employees",
    "headers": {"Authorization": "Bearer {{secret \"crm_token\"}}"}
  }
}
```

An execution reads only the secrets of its workflow's tenant. A name the tenant does not have fails the node with `secret not found: <name>`.

## What executions show

Before a node result, a retry error or the execution's error is stored, every secret value of 8 characters or more in it becomes `***`, the way CI systems mask logs. A CRM that echoes the token back, or an error that quotes a secret URL, shows `***` in the execution. Values shorter than 8 characters are not masked, so keep credentials longer than that.

Masking happens when the result is recorded, so later nodes read `***` as well. A node that needs the credential reads it with `secret` itself instead of taking it from an earlier result.

## Encryption

Secrets are stored in PostgreSQL encrypted with AES-256-GCM under the key `serve` gets as [`OPERION_SECRETS_KEY`](/docs/operating/configuration), which never goes into the database. Each value is bound to its tenant and name, so a row copied to another tenant does not decrypt.

Keep the key: secrets saved under one key cannot be read with another, and executions that need them fail until the right key is back. Rotating the key and reading secrets from an external store such as Vault are not supported yet.

`operion run` has no database; it reads secrets from a JSON file given with `--secrets`, see [run a workflow locally](/docs/getting-started/run-locally).
